# ARC3-RUN-002 C0 初回基準線診断

## 対象と前回値

- Kaggle submission `57527856`、Notebook version 5、評価対象コードcommit `f8ace66bec06440c21362b1afbf0dec0da99dd7f`。
- 公式public score: `0.00`。公式結果記録は `ARC3-RUN-002_S1-初回公式基準線_20261022.md`。
- 公式履歴からゲーム別到達・操作数は取得できないため、0.00の内部構成は未観測。
- ローカルの先行結果14/183 levels、1/25 complete gameは異なる実行系の公開サンプル進捗であり、本Notebookのprevious/current/deltaには混ぜない。

## 原因層の照合

1. `MyAgent.__init__` は保存済み学習状態を読み込まず、空の `HDS学習系統()` を新規生成する。
2. `NOT_FINISHED` を受けると `公開観測から候補を照会する` を一度実行する。既存の共通観測経路と候補語彙は出力の `実行許可` をfalseに固定し、環境stepを呼ばない。
3. `MyAgent.is_done` はその候補照会の後にtrueを返す。`choose_action` は `NOT_PLAYED` 初期化時のRESET以外にActionを返さず、初期化後の `NOT_FINISHED` では境界違反を送出する。
4. 提出物構築器は `入力/` と `記憶/` をbundleから除外している。OFFLINE実測では初期の進行中観測から候補なし・Action 0回・HOLDだった。

この静的経路は「提出agentに初期観測後の実行Action経路がない」ことを直接示す。公式score 0.00と整合する最優先の故障候補である。ただしKaggleの個別実行ログがないため、公式scoreの因果内訳や全ゲームの実際のAction数までは断定しない。

## 優先課題の選定

最初の改善対象は「公開観測後に候補を記録して永久HOLDする提出agentのAction経路」とする。単にHDSの学習資料を増やしても、現行agentには候補からSDK Actionへ至る経路がないため、候補の量ではなく実行制御が先行故障である。

### 保持条件

- HDS HOLDを確定扱いに偽装しない。
- `実行許可`の自己申告だけで実行しない。Actionは現在観測の指紋・HDS根拠・`available_actions`・引数を照合する。
- game/level IDによる分岐、答え表、固定操作列、hidden情報を使わない。
- SDK `step`は一つの経路から一回だけ呼ぶ。各応答を再観測してから次を選ぶ。
- 候補語彙、既存の14/183公開進捗、HDS v0.4.2の中核を保持し、横断回帰で悪化を検出する。

## C1への引継ぎ

C1では、HDSが明示根拠を返した一意の候補をSDK Actionへ接続する限定制御を検討する。候補がHOLDのままでもActionが必要な場合に備え、HDS確定Actionと探索Actionを区別できる必要がある。現行の明示済み探索方針は見当たらず、探索Actionは別の根拠・評価単位として設計し、未検証の無差別操作を追加しない。C1指示書を先に作成し、その範囲内で小さく検証する。
