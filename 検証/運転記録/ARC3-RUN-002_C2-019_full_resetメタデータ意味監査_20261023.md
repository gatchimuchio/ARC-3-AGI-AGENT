- 判定: **固定ローカルSDKでは`full_reset`は初期化応答のイベントmetadata。C2-018のno-op flag差分は、同一run順probeで初回Actionの差分件数と一致。policy・candidate v4を維持。**

## SDK source

`python -m uv run --locked`で実行した環境は`arcengine 0.9.3`、`arc-agi 0.9.8`。

- `arcengine/base_game.py`: `perform_action()`はAction処理ごとに最初に`_full_reset=False`へ戻す（line 204）。raw responseへ値を載せる（line 247）。
- 同ファイルの`handle_reset()`は通常条件で初回（`_action_count == 0`）のRESETを`full_reset()`へ送り（lines 305–316）、`full_reset()`が`_full_reset=True`を立てる（lines 318–324）。
- `arc_agi/local_wrapper.py`の`reset()`は`GameAction.RESET`を`perform_action(..., raw=True)`へ渡し、応答を保持する（lines 181–204）。このためprobeの初期観測には`True`が届き、その後の最初のゲームAction応答は`False`となる。

したがって、初期化後の最初のActionが盤面・levelを変えない場合、持続的な環境状態に変化がなくても`full_reset`は`True → False`と変わる。これはゲーム進捗を表す値ではない。ここで確認したのはローカル公開SDKのみであり、Kaggle remote APIの契約には一般化しない。

## 固定dev probeとC2-018照合

C2-018と同じsplit seed `20261022`、公開dev 5環境、Action seed 7/31/73を用い、各runで初期RESET後の最初のActionだけを実行した。game識別子、盤面、Action列、イベント単位の出力は保存していない。

| seed | 初期RESET `True` | 初回Action `True→False` | 初回Action no-op | no-opかつ`True→False` | C2-018 run別差分件数との一致 |
|---:|---:|---:|---:|---:|---|
| 7 | 5/5 | 5/5 | 2 | 2 | 5/5 run |
| 31 | 5/5 | 5/5 | 1 | 1 | 5/5 run |
| 73 | 5/5 | 5/5 | 2 | 2 | 5/5 run |
| 合計 | 15/15 | 15/15 | 5 | 5 | 15/15 run |

各seedの同一run順で、C2-019の「初回Actionがno-opかつ`True→False`」件数ベクトルとC2-018の「no-op中の`full_reset`差分」件数ベクトルが完全一致した。15 run中、初回Actionのno-opは5件で、その5件全てで`full_reset`が切り替わった。C2-018全体の差分件数5もこれで説明できる。既存C2-018 artifactには個別イベントの識別子がないため、イベント単位のjoinやtrajectoryの再構成は行っていない。

C2-018で測ったframe数差分17件の意味はこのsource監査では扱っていない。Action集合変化・state遷移が0だった前回結果も別指標のまま保持する。
