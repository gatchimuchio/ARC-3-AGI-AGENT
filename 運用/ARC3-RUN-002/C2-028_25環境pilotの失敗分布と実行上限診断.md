# C2-028 25環境pilotの失敗分布と実行上限診断

## 目的

C2-027は同一開始状態25件でlevel進捗+44を示した一方、WINは0で、全25 runが`gave_up`、4件が時間上限に到達した。private集計を能力の確定・公式性能と読み替えず、成功／停滞／後退、Action上限・runtime上限、model/tool timeout、GAME_OVER、token telemetryの範囲を既存artifactから切り分ける。

## 対象と制約

- candidate: private Kaggle kernel `tecchannn/arc3-model-guided-c2-025` version 5の完了出力。
- previous: `出力/ARC3-RUN-002-local/C2-025-v4-public-25-retry.json`。開始状態は`出力/ARC3-RUN-002-local/C2-026-start-check.json`とcandidate initial eventを使って直接照合する。
- C2-027が保存したcomparison JSON、benchmark、per-game events、transcripts、kernel log、output hash manifestを使う。すでにある出力の再実行・再取得は必要な照合に限る。
- notebook、model、prompt、solver、HDS、公式入力、AGENTS.md、制御/現在状態.jsonは変更しない。新しいKaggle run、Competition Rerun、提出、採点を行わない。
- game IDは証拠の対応付け・集計だけに使い、policy上の条件分岐や固定actionの作成に使わない。

## 分析項目

1. 全25件のID集合とinitial board/state/level一致を再確認し、同条件previous/current/deltaを集計する。
2. 完了level、Action数、80 Action cap、1,200秒runtime cap、final state、WINの分布を分類する。runtime値の意味をbenchmark時刻・kernel logと照合する。
3. eventsからno-op、level completion、GAME_OVERを集計し、baseline同指標と比較する。
4. transcript/kernel logから初回接続失敗、request timeout、tool timeoutを分類する。timeoutの有無をepisode失敗の断定理由にせず、未達・上限到達と併記する。
5. token telemetryのbenchmark最終欄、per-action history、solver_noteの整合性を検査する。
6. どの範囲まで公開25件のgeneralization evidenceと言えるかを定め、次の一課題を選ぶ。公式候補への昇格を決めない。

## 受入条件

- 25件すべてを照合し、欠損・IDずれ・開始状態不一致があれば別途明示する。
- previous/current/delta、cap到達、WIN、timeout、eventおよびtelemetryの根拠とhashを記録する。
- 観測と解釈を分け、public/privateの範囲を明示する。
- 次のtaskを一つだけ指示書として発行する。正のlevel deltaを理由に公式提出を自動実行しない。

## 実行結果

2026-10-23 UTCにC2-027 artifactsを解析。kernel version 5は`COMPLETE`。25件のbaseline/candidate/event ID集合は完全一致、initial board/state/levelは25/25一致。benchmarkの`start_time`から`end_time`まで15,657.695秒（4時間20分57.695秒）。各gameの`final_wallclock_seconds`はgame run順で累積し、benchmark全経過時間と整合したため、隣接game間の差からper-game elapsedを算出した。

| 区分 | 件数 | baseline level | candidate level | delta |
| --- | ---: | ---: | ---: | ---: |
| 改善 | 22 | 2 | 47 | +45 |
| 同等 | 2 | 0 | 0 | 0 |
| 後退 | 1 | 1 | 0 | -1 |
| 合計 | 25 | 3 | 47 | +44 |

同等は`sk48-d8078629`と`wa30-ee6fef47`（各0 level）。後退は`tn36-ef4dde99`（baseline 1、candidate 0）。candidateは全runが`gave_up`でWIN 0。21件は80 Action上限に達し、4件は1,200秒runtime上限に達した：`sk48-d8078629` 69 Action/1,201.5秒/0 level、`bp35-0a0ad940` 57/1,200.0/1、`r11l-495a7899` 46/1,201.7/3、`sp80-589a99af` 54/1,202.5/1。4件の合計はcandidate 5 level、同baseline 1 level（delta +4）。

eventsはinitial 25、action 1,906、analysis 762。candidateはlevel completion 47、GAME_OVER 7、可視盤面無変化Action 68/1,906（3.57%）。baseline explorationはGAME_OVER 15、no-op 137/2,000（6.85%）。action eventにinvalid actionの専用集計欄はないため、違法Action 0とは主張しない。

kernel logは開始後のanalyzer `ConnectionError`と再試行、action 70/58のrequest timeoutを記録。`sk48`と`bp35`のtranscriptにもrequest timeout、`r11l`と`sp80`には探索tool timeoutがある。`lp85`にもtool timeout記録があるが80 Actionに到達し5 levelを完了したため、timeout一件を直ちにepisode失敗の十分原因とは扱わない。4件のruntime capとログ上の異常は別々に記録し、次工程で個別の因果を調べる。

per-action history `generated_tokens`の合計は2,134,037。3つの時間上限episode（`bp35`, `r11l`, `sp80`）ではsolver_noteの`tokens=`がhistory合計より28,229多い。全25 runの`final_generated_tokens`は0のため不採用。消費tokenの精密比較にはtelemetry修正または独立集計が必要。

この25件では同一開始公開環境に対する広いlevel進捗改善を観測した。ただしhidden環境、別乱数、再実行での再現性、全ゲーム勝利は確認していない。80 Action上限が多くのrunで先に到達したため、WIN 0のみから無制限solverの勝利能力を否定できない。private改善値を公式scoreへ換算しない。

## 次工程

C2-029で、既存の最初3公開環境（`sk48`, `tn36`, `m0r0`）を同じ初期条件から再実行し、offline-only Action capを80から160へ広げる小規模horizon検査を行う。per-game runtime 1,200秒、逐次1 pass、model/prompt/solver policy固定を維持し、action cap到達とruntime cap到達を分離して記録する。これはprivateの追加開発試験であり、公式提出・昇格ではない。
