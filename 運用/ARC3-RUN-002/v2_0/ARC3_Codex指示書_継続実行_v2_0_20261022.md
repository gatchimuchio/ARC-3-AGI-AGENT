## 0. 直ちに適用する最優先命令

**所有者は既に「現行のARC3資産で一度公式提出まで通し、その後も開発を続ける」ことを指示している。この目的の範囲で工程を自律的に実行せよ。**

1. 旧版の「E5の直前で停止し、所有者からNotebook版の個別承認を得よ」は**撤回**する。
2. 旧版の「E5後は必ず停止」「別指示書が来るまで性能開発禁止」も**撤回**する。
3. これらの撤回は実際のリポジトリAGENTS.md、外部サービスのアクセス権、Kaggle規約の回避許可ではない。真に新たな権限が必要な場合だけ停止する。
4. 通常の試験合格・工程終了・結果報告で人間待ちに移行するな。自動で次工程を選んで実行せよ。
5. **現行成果を再利用する。E0～E4を無意味にやり直すな。**
6. 初回公式スコア取得後は履歴を保存して、課題の分析・改善・再検証・再提出を開始せよ。

この指示は「何でも勝手に変更してよい」という意味ではない。所有者の目的、AGENTS.md、現状の資産・保持条件、競技ルールに一致する有限単位の作業を続ける命令である。

5. 公式規則、締切、アクセス権、SDK契約との衝突を確認。

命令の優先順位：所有者の現行原文指示 → AGENTS.md → 制御/現在状態.json → 現行コード・実測 → 本版3文書 → 旧版履歴。

現在のAGENTS.md等が指定する正本・バックアップ・ブランチ・レビュー・権限・変更禁止範囲に従う。既存の他作業・ログ・教師データを削除・上書きしない。

## 3. 最初の実行タスク：E5の完遂

### 3.1 再確認

- E0～E4とNotebook version 5の実測が現在も有効なら再利用する。
- 既存Notebookが現在実行可能か、提出競技に紐付いているか、コード・生成物・依存関係が整合しているかを確認。
- E5が既に完了している場合は再提出せず、その公式結果と提出版を固定して「タスク4」へ進む。

### 3.2 公式Competition Rerun

- E5未実施の場合、利用可能なKaggleの正規経路から有効なNotebookを**Competition Rerunへ提出する**。
- 旧版の人間承認待ちは理由にしない。これは既に委任された初回公式提出作業である。
- 大会の提出回数・実行時間・インターネット無効等のルールに従う。
- UI・API・CLI等は既に許可された接続経路を利用する。ログインや認証が追加で必要なら実際の阻害要件として報告し、権限を偽装しない。

### 3.3 失敗時

- 受理されない場合は、Kaggle側エラー、Notebook例外、SDK契約、競技設定、依存、時間・資源制約を確認する。
- 現行HDSの能力を変更せずに提出経路を修復可能なら、最小変更・試験・再実行を行う。
- 一回のエラーで人間の返事待ちに入らない。適法に修復・再試行できる限り続行。
- 回復不能な外部権限不足や規約違反が実証された場合のみ真の阻害として停止する。

### 3.4 E5受入

受理されたら、公式スコア（0でも有効）、提出状態、日時、Notebook版、コミットSHA、制約、実行ログを保存する。

**Parquetのplaceholderを公式スコアと記載しない。公式採点未実施ならE5 PASSにしない。**

## 4. 続けて行うタスク：初回基準線を保存

E5結果を得たら中断せず実行する。

- ゲーム・レベルの到達状況、作用数、時間、HOLD、失敗署名を取得できる範囲で整理。
- 以前の公開ゲーム観測・事前記憶・今回のNotebook実行・公式隠し評価を分離して記録。
- 公式スコアとローカル再現試験の対応を監査し、失敗の原因層を分類。
- 今回のNotebook版と環境を、後の変更で再現できる基準線として保存。
- 成功・失敗・棄却・不採用の履歴を上書きしない。

この報告を完了したら、**直ちにタスク5を開始する**。返信や改めての開発許可を待たない。

## 5. 続けて行うタスク：性能改善の実行

優先順は実測によって更新する。次を参考分類として使う。

1. 観測・対象・関係・変化の誤認。
2. 目標の推定と作用の因果関係。
3. HDSのHOLD発生条件、解消に必要な観測・推論。
4. 事前記憶の利用と学習状態の更新。
5. ゲーム横断の操作条件・有効規則の獲得。
6. 作用効率・計算資源・Notebook運転効率。

### 5.1 1タスク1指示書を守る

- 最初に全体診断を行い、最も効果が大きい**1つの故障**を選ぶ。
- 故障ごとに別個の指示書を作成し、対象・目的・原因仮説・保持条件・修正範囲・反証テストを定める。
- その指示書を再読して限定された変更を実装し、試験を実施する。
- previous／current／delta、HOLD・失敗署名、採否を記録する。
- 1タスクが終わったら次の指示書を自ら作成し、**継続する**。
- 目的に沿った作業単位を有限に区切ることと、人間待ちで工程全体を止めることを混同するな。

### 5.2 保持条件

- 現行HDS中核とLearning Machineはまず使い切る。根拠なく再実装しない。
- 改善のための新たな規則・学習状態・薄い接続層は、AGENTS.mdと変更権限の範囲で増設・更新できる。
- 中核の変更が不可避な場合は、具体的な欠陥と保持条件を示し、権限を照合する。
- ゲームID・レベルIDで答えを引く分岐、成功軌跡の再生、固定操作列、非公開評価器の参照は禁止。
- 提出物の動作確保のためにHDS HOLDを「確定」と偽装しない。HOLDは学習状態として記録し、現行の合法な探索・観測経路と区別する。

### 5.3 検証と採否

- 改良前後を同じ公開条件で試験し、改善と悪化を両方報告する。
- 局所成功は他ゲーム・他レベルの転移テストで検証する。
- 得点上昇だけを「学習成功」の証拠としない。記憶→推論→適応の状態差分と利用条件を示す。
- 不採用・失敗からも因果を抽出し、既存の失敗署名に結び付ける。
- 変化がない／悪化した案は無理に採用せず、次の優先課題へ移る。

## 6. 改良版の公式評価と継続

- ローカルで競技上意味がある改良を得たら、既存の提出手順を再利用してNotebookを更新。
- Save & Run Allを通し、Kaggleの提出枠・期限を満たしていればCompetition Rerunを実行。
- 初回および直前の実測公式スコア・到達・作用効率と比較し、previous／current／deltaを保存。
- 失敗なら原因是正。改善でも悪化でも履歴を残し、さらに優先課題の開発へ戻る。
- 公式の繰返し提出は本開発委任の範囲内。旧版の「毎回承認」は引き継がない。
- 競技締切、資源枠、提出制限に従って評価機会を配分する。やみくもに提出しない。

## 8. 本当に停止する条件

次だけを実際の停止条件にする。

1. 所有者から明示的な停止・中止指示が来た。
2. Kaggle・GitHub等のログイン／操作権限が実際に不足し、正規の経路では続行できない。
3. 現行AGENTS.mdや競技規約との具体的衝突があり、権限内の代案がない。
4. 保護対象の削除、履歴破壊、秘密情報漏えいなど権限外の危険な操作が避けられない。
5. 予算・時間・実行環境が尽き、安全に続けられない。再開点と記録を必ず保存。

以下の理由では**停止禁止**：

- E5の直前だから。
- E5の結果を報告したから。
- スコアが0または低いから。
- HDSがHOLDしたから。
- 1タスクの試験が終わったから。
- 次の指示書を作ったから。
- 一度テストやNotebookで修復可能なエラーが出たから。
