## 0. 原文目的・今回の是正

所有者の元の指示は「現行リポジトリの資産を使って一度公式提出まで通し、続いてその結果を使って開発する。開発はCodexへ委任する」である。

したがって本仕様の成立条件は次の全て。

1. 現行資産による**初回Competition Rerun（公式評価）を実行**する。
2. 公式結果と失敗を基準線として残す。
3. 基準線に従って学習・一般化・攻略能力の改良を**継続**する。
4. 有効な改善を確認したら、競技条件内で再提出して実測を更新する。
5. 各実行単位は自己完結した作業指示・証拠・履歴を持つ。**通常の工程境界は停止理由ではない**。

旧版は「E5直前の個別承認」と「E5後の別指示待ち」を追加し、既に与えられた作業権限を不当に縮小した。本版では両方を撤廃する。所有者の新指示、実際のアクセス権、リポジトリAGENTS.md、Kaggle規約に反する操作まで許可するものではない。

## 2. 指示の正本と作業権限

優先順位：所有者の現行原文指示 → リポジトリAGENTS.md → 制御/現在状態.json → 現行コード・試験・運転記録 → 本版3文書 → 旧版3文書・履歴。

- 本版の初回公式提出指示は、上記の所有者原文から導かれた**既存の実行委任**に含まれる。旧版のE5個別承認要件を引き継がない。
- Codexは利用可能な既存のGitHub・Kaggle連携権限を正当に用い、既に指定された競技へ提出する。権限のないログイン、資格情報の転用、規約違反は行わない。
- 元指示とAGENTS.mdが実際に衝突する場合は、衝突する行・対象・権限を明示して問題を解決する。単なる「慎重さ」「外部送信だから」は独立した停止理由にならない。
- 以前の制御/現在状態.jsonには「自動遷移:false」があった。これは観測時点の状態値であって、所有者の新たな継続実行指示を無条件に無効化する上位命令とは扱わない。現在の意味定義とAGENTS.mdを照合し、正規に状態更新できるなら履歴付きで更新する。値だけを理由に人間待ちを再発させない。
- 公式提出の完了後も初回指示の目的は終了しない。性能開発・再評価への遷移はあらかじめ承認された工程の一部と扱う。
- 所有者への報告は判断材料の提供。明示的な採否変更や新権限が必要な場合を除き、報告を人間待ちゲートに置換しない。

## 4. 提出用実行契約

1. 公式環境の観測を取得し、その観測時点・状態を記録する。
2. 既存のHDS観測・学習・判断経路を通し、判断と根拠を得る。
3. 公式SDKの行動形式へ適合させ、公式Runnerに返す。
4. 環境のtake_action／env.stepは**一つの経路**で実行し、二重作用を防ぐ。
5. 実行後の状態・報酬・進捗・作用数・HOLD・失敗理由を対応させ、次の学習判断へ戻す。

### 4.1 HDSのHOLDと提出の関係

HOLDは「HDSが確定作用を許可していない」という学習・判断状態であり、競技全体の永久停止を意味しない。

- 未確定候補を「HDS確定」と偽装して実行しない。
- HOLD状態の観測・解消条件を記録し、現行の適法な実行経路があれば使用する。
- 公式環境が合法作用を要求する場合は、現行の**明示された探索／観測方針**・SDK契約の範囲で運用し、HDS確定作用と探索行動の出所を必ず区別する。
- 存在しない承認、ゲーム固有の成功軌跡、ID別固定操作列で穴埋めしない。
- HOLDや低得点が発生しても、Notebook実行・公式評価・改善の進行を一律に停止してはならない。合法な動作を実装できない真の契約障害だけを停止候補とする。

### 4.2 汎用性要件

- ゲームID・レベルIDを条件に答えを直引きしない。
- 固定作用列、正解の再生、非公開評価情報、環境内部状態の不正取得を用いない。
- 既存の観測資産・成功軌跡は原因・規則の抽出素材であり、答え表として使わない。
- 学習の証拠は記憶→推論→適応の状態遷移に置く。スコア上昇だけを学習の証拠にしない。
- 単独ゲームの局所最適化より、条件を他ゲーム・他レベルへ転移できる横断規則を優先する。

## 5. 連続実行の制御モデル

| 状態 | 判定 | 次の動作 |
| --- | --- | --- |
| 前工程の証拠が有効 | PASS | 無断の停止を挟まず次工程へ |
| 既存成果と最新状態が一致 | REUSE | 成果を再利用し重複作業を省く |
| ローカル試験・Notebook失敗 | FIXABLE | 原因特定→最小修復→回帰→同工程再試行 |
| 公式提出でエラー | RETRYABLE | 公式制限内で原因修正→再提出 |
| HDS判断がHOLD | LEARNING_HOLD | 状態を記録し、適法な観測・推論・学習を継続 |
| 所有者が止めた、規約違反が必要、権限不足、保護対象の無断破壊が必要 | REAL_BLOCK | 必要な相手へ必要最小限の判断を求め停止 |
| 期限到達・処理環境が尽きた | CHECKPOINT | 次回再開可能な履歴・未完工程を固定 |

**PASS・REUSE・FIXABLE・RETRYABLE・LEARNING_HOLDを「Owner承認待ち」へ変換しない。**

## 6. 1タスク1指示書と継続運転の両立

- 1回の改修課題は1つの限定した指示書として発行し、その課題の実装・試験・記録を完結させる。
- 各単位の着手前にAGENTS.md・制御/現在状態.json・当該指示書・最新コードと試験を再確認する。
- 成功・失敗・HOLD・採否と次の優先課題を記録し、**次の指示書を自動的に作成して作業を続ける**。ルート権限の変更はしない。
- 新しい指示書には対象、目的、変更許可、保持条件、観測・検査、終了条件を記す。
- 人間向け報告は工程完了ごとに可能だが、通常の作業継続の条件にはしない。
- AGENTS.mdが定めるmain・ブランチ・バックアップ・正本・レビュー運用に従い、失敗履歴を消さない。

## 7. 工程と受入条件

### S0：再開状態の観測

E0～E4の完成物・Notebook version 5・main SHAを再確認し、有効な実績を再利用する。新しい検証の必要性が観測されない限り、E0～E4を最初からやり直さない。

### S1：初回公式評価

現在の有効なNotebookでCompetition Rerunを実行し、受理状態と公式スコアまたは公式エラーを実測。E4のParquet内placeholder scoreを公式スコア扱いしない。E5が無効なら原因を直し、必要な再試行を続ける。

**S1の受入**：Kaggle公式評価の結果が取得でき、コミット・Notebook版・環境・時刻・ログと対応している。

### S2：基準線固定

スコア、ゲーム／レベル到達、作用数、HOLD、失敗署名、実行時間、主要な失敗原因を保存。実測値がない項目は「未観測」とする。**S2を完了したらS3へ自動遷移**。

### S3：性能開発

1. 観測、対象・関係理解、目標推定、作用因果、HOLD、記憶・推論・適応、資源効率の失敗箇所を棚卸し。
2. 改良優先度を「効果／横断転移／修正範囲／破壊リスク／検証可能性」で決定。
3. 1課題1指示書で局所的に改良し、同条件の前後比較で採否。
4. 固有IDに依存しない横断試験を通し、有効な規則を再利用。
5. 次課題へ継続。途中報告は必要に応じて行うが、次課題開始の承認待ちは作らない。

### S4：改良版の公式評価

再提出価値がある改良を得たら、Kaggleの回数・期限・公開条件内でNotebookの再検査とCompetition Rerunを実行し、S1とのprevious／current／deltaを記録。再提出ごとに個別のOwner承認を強制しない。

## 8. 品質保証の対象

| 評価対象 | 判定方法 |
| --- | --- |
| 提出経路 | Kaggleが実評価を受理し、結果を返す |
| SDK適合 | 契約、GameAction、作用数、二重stepなし |
| HDSの因果 | 観測→判断→実行→状態遷移の根拠が追える |
| 学習 | 記憶・推論・適応の更新が別状況で再利用可能 |
| 性能 | 公式スコア、到達、作用効率、時間・資源 |
| 回帰 | 変更前後の同条件比較と既存能力の保持 |
| 履歴 | SHA、提出版、ログ、失敗署名、採否、previous/current/delta |

旧実績、今回の再実行、Notebook仮の出力、Kaggle本採点を混同しない。成功と失敗をどちらも保存する。

## 9. 停止条件と非停止条件

**停止する：**

- 所有者の明示停止・中止。
- AGENTS.mdやKaggle規約との具体的衝突で、現在与えられた権限では解決できない。
- 必須の資格情報・接続許可を持たず、正規の方法で進めない。
- 保護対象の破壊・権限外変更・秘密情報の公開など、実行権限を越える操作が不可避。
- 証拠により次の安全な操作が存在しない重大な故障。

**停止しない：**

- 既に委任された公式提出の実行前。
- E0～E5の工程境界や単なる報告タイミング。
- スコア0、HDSのHOLD、個別のテスト失敗、修復可能なNotebook障害。
- 初回公式スコアの取得後、基準線の保存後、各局所改良の終了後。
- 新しい指示書の生成・再読という通常の作業管理のため。
