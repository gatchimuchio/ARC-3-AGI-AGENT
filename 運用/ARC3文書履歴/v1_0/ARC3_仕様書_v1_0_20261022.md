## 1. 適用原則

1. **提出経路の成立を最優先**。学習機械の改良、新規攻略ロジック、性能最適化は初回の公式提出後まで実施しない。
2. 現在のHDS・学習機械・公式入力・既存観測資産を使用する。既存のHDS中核を改変しない。
3. 公式提出の成功は、得点の高さやAGI能力の証明ではない。**公式評価側で有効な提出が受理され、評価結果を取得できたこと**を意味する。
4. 過去の観測、ローカル再現、提出物の生成、Kaggle実評価を別個の状態として記録し、代替しない。
5. ご主人様が各段階の採否を決め、Codexは根拠を提出する。とくに公式送信と改善フェーズ開始は明示承認制とする。

## 4. 今回の納入物

### 4.1 初回提出フェーズ（最優先）

1. **公式インターフェース適合層**：既存HDSの判断から公式MyAgent.choose_actionの返却値への最小変換。
2. **Kaggle Notebook提出パッケージ**：必要コード・一般化規則・適法な依存物をオフラインで実行可能にする最小構成。
3. **ローカル再現手段**：同じ提出物を同じ入力・環境で再実行し、返却作用と根拠を記録。
4. **実行ログ**：入力、HDS判断根拠、HOLD、実際の作用、各段階のエラー、前後差分。
5. **Kaggle受理記録**：NotebookのSave & Run Allの結果、および別工程であるCompetition Rerunの結果。
6. **初回基準線報告書**：コミット、環境、Notebook版、実測結果、未解決問題、次期改善候補を固定。

### 4.2 初回提出フェーズで納入しないもの

- HDS中核の作り直し、学習機械の世代更新、全25ゲームの個別攻略。
- 公式サンプルへの最適化、ID別分岐、解答軌跡再生、固定作用列、無根拠な探索。
- 得点向上のための大規模再設計、外部LLM API連携、秘密情報の配布。

## 5. 最小実行契約

### 5.1 データと制御

1. 公式環境の観測を取得する。
2. 既存の共通観測経路を通してHDSに入力する。暫定候補は実行許可に昇格させない。
3. HDSが観測根拠に基づき作用を**確定**した場合だけ、公式のGameActionへ変換する。
4. HDSのHOLD、根拠不足、非合法作用、観測の不一致を検知した場合は、虚偽の確定扱いにせず障害記録と停止条件へ送る。
5. 公式エージェントは確定した作用を公式契約通りに返す。
6. 公式環境から得られた状態遷移を記録し、次判断の入力に戻す。

### 5.2 作用実行権の単一化（重要）

- 公式Starter側はMyAgent.choose_actionが返すGameActionを受け、実行側がtake_action／env.stepへ渡す。
- 現行の接続/ARC3境界.pyの「作用を排出する」はenv.stepを内部で呼ぶ経路がある。
- この両者を無条件に結線すると**同じ判断を二重実行**する危険がある。
- 提出用アダプタは「**作用を返すだけ**」を基本とし、環境実行は公式Runner側の一箇所に限る。
- ローカル既存経路を再利用する場合も、実行権の所有者は必ず一つにする。観測・作用の一対一性をテストする。

### 5.3 HDSの認可とHOLD

- 「判定＝確定」という文字列の存在のみでは、HDSの実行許可証明にならない。根拠・由来・現在観測との対応を確認する。
- 接続/共通観測経路.mdで実行許可がfalseの候補を、そのまま実行してはならない。
- HOLDを乱数、適当な方向キー、既知解答、成功軌跡コピーで埋めない。
- 公式提出契約でHOLDを合法に返せない場合、**契約上の障害として停止**し、代替案の承認を求める。提出成功を偽装しない。

### 5.4 汎用性と禁止事項

- ゲームID・レベルIDをキーにした分岐、事前に固定された操作列、レベル別の答えの直引きは不可。
- 公式Starterの例示用個別ゲーム攻略処理（例：ls20分岐）を製品ロジックへ転用しない。
- 評価器の内部、非公開の正解情報、非許可の隠し状態を参照しない。
- 既存資産は記憶・観測・規則抽出の一般化された入力として使用し、軌跡の逐次再生を攻略とみなさない。

## 6. 提出環境・品質条件

| 分類 | 必要条件 |
| --- | --- |
| SDK | 公式Starterと競技指定の署名・戻り値・依存条件に一致 |
| 実行方式 | Notebook内のオフライン実行で成立。外部ネットワークや外部LLM APIに依存しない |
| 時間・資源 | Kaggleの現行競技制限内で終了。公式規則の再確認を行う |
| 梱包 | Starter標準の自動ビルドが単一ファイルしか収めないなら、追加HDS依存物を含む最小梱包を実装 |
| 情報管理 | シークレット、非公開コード、許諾不明の教師解答・再生軌跡を提出物へ含めない |
| 再現性 | 提出コミット、パッケージ版、入力、依存環境、実行ログを固定 |
| 証拠 | 実行済みであることと、得点を得たこととを区別 |

Kaggle公式のCPU/GPU実行時間やソース公開条件等は着手時に現行の公式ルールで再確認する。変更があれば優先して本仕様との差分を報告する。

## 7. 段階別受入試験

| Gate | 試験内容 | 通過条件 |
| --- | --- | --- |
| E0 | 現行状態と指示再確認 | SHA、未コミット変更、使用資産、規則の台帳がある |
| E1 | 単体試験 | SDK型、HDS認可、HOLD、違法作用、観測更新、二重実行なし |
| E2 | ローカル統合試験 | 公式公開ゲームを使った実動作と再現ログを取得 |
| E3 | Notebook前試験 | オフライン・依存・梱包・秘密情報・資源制約を確認 |
| E4 | Kaggle Save & Run All | 提出用Notebookの完走と生成物を確認。ここでは実評価受理とみなさない |
| E5 | Kaggle Competition Rerun | 公式提出が実評価され、結果・状態を確認できた |

- **初回の技術的完了＝E5通過**。スコアが0でもE5で有効受理なら技術経路は通過。一方、高得点でもE5の記録がなければ「公式提出済」は不可。
- E4の生成物（例：submission.parquet）を得ただけではE5の代わりにならない。
- E5実行前にご主人様へE0〜E4の結果と提出対象を提示し、明示的承認を取得する。
- E5で障害があれば現行能力のまま原因を是正して再試験。得点改善開発には自動で移らない。

## 8. 初回提出後の性能開発要件（別指示）

E5結果を基準線として固定後、次の有限単位を繰り返す。

1. **観測**：失敗・HOLD・成功遷移・資源超過を全件収集。
2. **原因の分類**：対象認識／関係抽出／目的推定／作用と因果／規則転移／HDS認可／環境接続。
3. **横断規則の抽出**：個別ゲーム固有の攻略法ではなく、別ゲーム・別状況でも成立する操作条件と学習状態を更新。
4. **局所改修**：仮説、期待する状態遷移、保持条件、破壊リスクを明記した最小変更。
5. **反証と比較**：前回と今回を同じ条件で試験し、previous／current／deltaと失敗署名を保存。
6. **採否**：ご主人様の判断で採用・保留・棄却。失敗した規則を無断で再採用しない。
7. **公式再提出**：ローカル改善が確認でき、競技上意味がある場合のみ別承認で実施。

スコアの目的はARC-AGI-3公式評価の向上。ただし指標は得点だけでなく、到達レベル、成功条件、無駄作用、HOLDの質、他課題への転移、再現性、失敗署名を併記する。RHAE方式の重みと効率は公式定義で確認する。

## 9. 停止・承認条件

以下に該当したらCodexは作業を止め、独断で境界を越えない。

- AGENTS.md・現在状態・ご主人様の指示の衝突。
- HDS基底変更、教師・公式入力原本の書換え、権限のない確定作用。
- 実際の公式送信が必要な段階への到達。
- Kaggleの規約、入出力形式、ライセンス、秘密情報に関する未解決障害。
- E5以降の改善フェーズ着手。

報告単位：対象／観測証拠／結果／previous／current／delta／失敗署名／残課題／ご主人様の判断事項。
