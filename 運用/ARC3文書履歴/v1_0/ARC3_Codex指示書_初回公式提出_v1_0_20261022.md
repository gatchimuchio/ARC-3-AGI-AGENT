## 2. 変更権限

### 許可する変更

- 公式SDKの返却形式に合わせるための**薄いアダプタ**。
- Notebookで動作させるための**最小梱包・依存導入・起動設定**。
- 上記の境界部分に直接必要なテスト、試験器、運転記録、新規の提出基準線資料。
- 既存の原理と公開SDK契約の対応関係を説明するドキュメント。

### 許可しない変更

- AGENTS.md、制御/現在状態.json、HDS/学習系統/v0.4.2、公式入力原本、記憶/事前記憶/v0.4の改変。
- 学習機械の仕様変更、全体再設計、既存資産の削除、既存試験の黙殺・書換え。
- ゲーム／レベルID別分岐、特定ゲーム用攻略、事前解答参照、成功軌跡の再生、固定作用列。
- StarterサンプルにあるID固有の攻略分岐（例：ls20）の模倣。
- HDSがHOLDしている箇所を乱数・当て推量・強制確定作用で埋めること。
- 外部LLM APIの必須化、認証情報・秘密のHDSコンパイラ等の提出パッケージ混入。
- force push、履歴書換え、mainの正本を壊す操作、検証根拠の削除。

範囲超過が避けられない場合は、対象／理由／代案／影響／承認が必要な事項を報告し、作業を停止する。

## 3. 作業単位と手順

### A0：現状固定・提出契約照合

- 最新の指示書類と現状を再読する。
- 実装の現存有無、依存関係、Windows実機経路とKaggleオフライン経路を把握する。
- 公式MyAgent.choose_actionの入力、出力、呼び出し元、take_action／env.stepの呼び出し箇所を特定する。
- 既存接続/ARC3境界.pyの「作用を排出する」が内部でenv.stepする経路との二重実行リスクを確認する。
- 公式Starterの標準ビルドがagent/my_agent.pyしか取り込まない場合、必要なHDS依存物を最小梱包する方式を確定する。

**A0成果**：現状台帳、提出契約対照表、作業対象ファイル案、変更禁止領域、暫定Gate判定。

### A1：提出専用の最小アダプタ

1. 既存の観測をHDSに伝え、HDSの既存判断を取得する。
2. 作用の根拠・許可状態を検証する。「判定＝確定」の文字列だけで認可済みとみなさない。
3. 許可された確定作用だけを公式GameActionへ変換する。SDKの列挙値・引数仕様を直接照合。
4. 公式choose_action側では原則作用を**返すのみ**とする。環境のstep実行は公式Runner側に一元化する。
5. HOLD、未確定候補、観測矛盾、違法作用は処理成功に偽装せず検出・記録する。公式契約が許す合法な表現を調べ、存在しなければ障害として停止する。
6. 実行前後の観測と作用の一対一対応を保持する。

**A1成果**：アダプタと単体試験。HDS中核のファイル差分なし。

### A2：結合・再現試験

次の最低条件を自動試験または実機ログで検証する。

| ケース | 必須確認 |
| --- | --- |
| 正常確定作用 | SDKに適合し、1回の判断につき1作用のみ実行 |
| 二重作用防止 | アダプタ返却と境界内部stepが同時実行されない |
| HOLD | 根拠不足を残したまま強行実行しない |
| 暫定候補 | 実行許可falseの候補を採用しない |
| 不正形式 | 不明な作用・範囲外座標・不正引数を拒否または明示的に停止 |
| 観測鮮度 | 古い観測・別状態に基づく作用を新状態へ誤適用しない |
| 履歴 | 判断、作用、環境遷移、失敗理由が対応付けて追跡可能 |
| 保持条件 | HDS中核、教師、公式入力、事前記憶の原本に無断変更なし |

- 公開25ゲーム全てを個別攻略する必要はない。接続の成立に必要な代表ケースと異常系を優先。
- 既存の成功記録を再評価する場合は「記憶資産の参照」と「今回の再実行結果」を区別。
- テストが未完了なら「全テストPASS」と記載しない。

**A2成果**：実行ログ、試験結果、previous／current／delta、失敗署名。

### A3：Kaggle Notebook準備

- 公式Starterの最新の必要ファイル構造・依存・提出手順に従い、Notebookを構築する。
- 提出実行に必要なHDSモジュールだけを梱包する。単一ファイル自動結合で不足する依存は明示的に追加する。
- Kaggleのオフライン環境で外部通信・外部認証・API課金に依存しないことを確認する。
- 使用する記憶・教師・規則の提出可否を大会ルールと照合する。秘密データ・答えの直引きは含めない。
- Notebook内のタイムアウト、CPU/GPU/メモリ上限、実行終了、生成物の整合を検証する。
- 可能ならWindowsで同一構成を再現し、環境固有の失敗を切り分ける。

現行リポジトリで案内されているWindows検証経路の例（必ず最新の接続/開発環境.mdに照合する）：

    python -m uv sync --locked
    python -m uv run --locked python 道具/開発環境確認.py --offline-game

新しい依存追加やネットワークアクセスが環境権限を超える場合は、規約・権限を確認して承認を求めること。

**A3成果**：Notebook本体、梱包手順、依存・機密情報・資源検査記録。

### A4：Kaggle Save & Run All（E4）

- NotebookをKaggle上でSave & Run Allし、完走・成果物・エラーを実測で確認。
- E4の完了だけで「公式提出成功」「実採点スコア取得」と報告しない。
- 失敗した場合は依存・SDK・Notebook・オフライン制約の原因を特定し、同じ提出能力の範囲で修正。
- ご主人様へE0～E4の根拠、提出予定Notebook、既知のHOLD／未解決問題を報告する。

**ここで停止し、Competition Rerunの実施許可を明示的に求めよ。**

### A5：Competition Rerun（E5、承認後のみ）

- ご主人様が具体的なNotebook版の公式送信を承認した場合のみ、競技の正式提出を実行する。
- 実評価の受理状態、Kaggleが返したスコアまたは明示された失敗理由、時刻、Notebook版・実装SHAを保存する。
- スコア0でも有効受理なら**技術的提出経路PASS／攻略性能は未達の場合あり**と正しく報告。
- 受理されなかった場合は**E5 FAIL**と報告し、問題と再試験案を示す。
- 成功・失敗を問わず、この指示書の作業はここで停止する。

## 4. 作業ごとの報告

各単位の開始時にAGENTS.md、制御/現在状態.json、実装状態を再確認し、終了時に次を必ず報告せよ。

1. 工程名、コミットSHA、対象ファイル、未コミット差分。
2. 実施内容とその目的。HDS／学習機械のどの部分を**変更せず保持したか**。
3. 観測した実行結果、テスト名と合否、再現方法。
4. previous／current／delta（同条件がないなら比較不可と明記）。
5. HOLD／失敗署名／障害原因／未観測情報。
6. 完了判定：PASS／FAIL／HOLD。
7. ご主人様が採否を決める必要のある事項。

推測、設計済、試験合格、ローカル再現、Kaggle実採点を混同しないこと。ログは追加方式で保存し、既存記録を上書き・消去しない。

## 5. 中断条件

次のいずれかで直ちに停止し、具体的な根拠と必要な承認を求める。

- リポ内指示と本指示に矛盾がある。
- HDSのHOLDを合法的に扱えず、虚偽の確定作用が必要になる。
- 保護対象への変更が必要になる。
- 秘密情報、個別正解、未許可データの提出混入が疑われる。
- 公式SDK、Notebook規則、公開期限と整合しない。
- ご主人様の未承認でE5に進もうとしている。
- E5後に攻略性能の開発へ進もうとしている。
