## 1. 工程設計

**A：初回公式提出 → B：基準線固定 → C：性能開発 → D：改良版再提出**。

## 3. フェーズA：現行資産による初回提出

| 工程 | 作業 | 完了の根拠 | 終了時判定 |

### A工程の不合格時

- A0～A4不合格：その工程の**接続・契約・提出物としての不具合だけ**を修正。HDSの攻略能力改良へ拡張しない。
- A5不合格：Notebook実行・依存・リソース・SDK適合を修正して再試験。
- A6不合格：受理形式、実行時間、環境差、通信・競技条件を原因分類。勝手に「受理済」にしない。
- HOLDが合法作用へ変換不能：具体的な契約矛盾と代替案を記録し、所有者判断まで停止。無作為作用で穴埋めしない。

## 5. フェーズC：提出後の性能開発（別指示書）

| 優先 | 改良テーマ | 取得する証拠 | 禁止する近道 |
| --- | --- | --- | --- |
| C1 | 観測→対象認識→関係抽出の欠陥 | 誤認識前後の状態差分 | 特定ゲーム画像・IDの答え引き |
| C2 | 目的推定と作用因果の欠陥 | 作用前後で目標へ接近／離反した原因 | 勘による作用列・成功履歴再生 |
| C3 | HDS認可・HOLDの欠陥 | HOLD理由、必要追加観測、解消条件 | 認可なし実行、HOLDの握り潰し |
| C4 | 学習機械の記憶→推論→適応 | 新旧学習状態、転移可能な条件、別課題の再現 | 成績向上だけを学習の証拠とすること |
| C5 | 実行効率と資源制約 | 成功到達と作用数／時間／負荷 | 未評価のスコアだけへの最適化 |
| C6 | 横断再検証 | 複数ゲーム・未知レベルでの条件成立 | 個別条件分岐の積み増し |

各C工程は**1課題・1指示書・1検証単位**。着手時にAGENTS.mdと制御/現在状態.jsonを読み直し、previous／current／delta、失敗署名、保持条件、採否を保存する。

## 6. フェーズD：改良版の再提出

1. C工程の変更を、初回基準線と同条件のローカル評価にかける。
2. 改善した項目と悪化した項目を全て報告する。
3. Kaggle提出の実行制約と梱包を再検査する。
4. ご主人様が承認した版のみE4→E5を再実施する。
5. 公式結果を新たな版として保存する。旧結果や失敗履歴を上書きしない。

## 7. Codex実行サイクル

各単位で以下の順序を固定する。

1. 指示原文、AGENTS.md、現在状態を再読し、対象と変更権限を確認。
2. 現在の実装・試験・記録を観測し、前回との差分を固定。
3. 最小変更を実施。
4. 変更に直接対応する試験から実行し、可能な範囲で回帰試験を行う。
5. 証拠付き記録を追加し、旧記録は保持。
6. Gate判定を報告して停止、または同一指示内の次の承認済み作業へ進む。

### 必須報告様式

| 項目 | 内容 |
| --- | --- |
| 状態 | 対象SHA／作業差分／工程番号 |
| 変更 | 変更ファイル、理由、保持した領域 |
| 証拠 | テスト名、入力条件、実測結果 |
| 比較 | previous／current／delta |
| 問題 | HOLD・失敗署名・競技規則との衝突 |
| 判断 | PASS／FAIL／HOLD、残課題、Owner承認要否 |

## 8. 権限ゲート

- ゲートG0：リポ指示と現在状態の不一致を解消するまでは改変しない。
- ゲートG1：HDS中核・教師・入力原本を改変する場合は初回提出タスクを停止。
- ゲートG2：E4の結果を確認するまでE5の承認を求めない。
- ゲートG3：**公式Competition Rerunはご主人様の明示承認が必要**。
- ゲートG4：E5後は必ず停止。C工程は新しい指示で開始。

## 9. 工程上の成功条件

- **第1成果**：現行ARC3資産から公式Notebookへ、改変範囲を限定した再現可能な接続。
