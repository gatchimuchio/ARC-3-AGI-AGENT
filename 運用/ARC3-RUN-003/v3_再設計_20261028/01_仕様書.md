## 1. 解く問題と成立条件

### 1.1 到達点の取り違えを禁止

1. **競技上の目標**：未知ゲームの全レベルを可能な限りクリアし、不要な操作を減らし、人間相対行動効率（RHAE）を上げて首位を狙う。正式に採点された低い得点は観測点であって完成ではない。
2. **学習機械の成立**：観測→仮説・操作→環境反応→原因修正→汎用記憶更新→別条件での行動改善、という因果を実験で示す。「HDSをimportした」「ログを保存した」「テストがPASSした」は成立証拠ではない。
3. **実動作するAgent**：公式SDK上でゲーム状態に合う合法Actionを発行し、作用前後を学び、目的まで複数の手順を計画し、レベル・ゲームの終了まで運転する。`RESET`だけ／初期観測後の`HOLD`終了は攻略Agentの合格条件を満たさない。
4. **正式提出**：`competition submission ID / Notebook kernel+version / source SHA / Kaggle最終status / errorDetails / 数値の公式score`を照合する。Notebookの`COMPLETE`、提出の`PENDING`、プレースホルダーParquetを公式RHAEと混同しない。数値`0.00`でも無エラーで確定していれば**受理された低得点提出**である。
5. **賞の受給資格**：高得点・順位とは独立。オープンソース条件とHDSの非開示原則を事前監査し、秘匿中核を無断公開しない。

### 1.2 公式の採点構造：ARC2の評価を流用しない

公式は各完了レベルについて `level_score = min(1.15, (human_baseline_actions / ai_actions)^2)` を基本とし、レベル番号（1からの通し番号）を重みにしてゲーム内集約、さらに全ゲーム平均を得る。未完了レベルはスコア上限の損失になる。詳細は公式定義に従う。`human_baseline_actions`が提供されない場合、ローカルでは**未観測**とし、RHAE近似値を公式値と称さない。

**したがって改善の順序は固定の「無駄手削減」一択ではない。** 未攻略ゲームの突破・後半レベルへの到達と、突破済みレベルの行動効率を、期待公式得点増分で評価する。全体予算の圧迫時は、非効率な挑戦を続けるより他ゲームの攻略を優先し得る。単一簡単レベルの超高速クリアは1.15上限により補填力が限られる。公式の環境外推論・ログ保存は行動数に算入されなくても、Notebookの実時間・メモリは消費する。

## 4. 必須構成：見て、動き、学んで、解く

`公式FrameData → 観測正規化 → 物体・地形・時間差分モデル → 操作の効果仮説 → 局所目標/レベルクリア条件推定 → 探索計画/価値・費用評価 → HDS判断と明示的な暫定探索Gate → GameAction一回 → 新FrameData → 検証・因果修正・汎用記憶更新 → 次の計画`。

各段階は独立に検査でき、実行判断と認識上の真偽判定を区別する。既存モジュールが責任を果たせるなら新規同型モジュールを乱造せず接続・拡張する。

### 4.1 観測と状態推定

- `frame`全層、64×64以内の色、`state`、`levels_completed`、`win_levels`、`available_actions`、`full_reset`、観測通番を取り込み、現在/直前/履歴を分離。
- セル差分だけでなく、連結領域、可動主体候補、境界、障害物、目標物、UI/メーター、数・色・方向・包含/接触/対称・周期、動的物体の追跡、座標系と移動可能性を推定。関係の不明・多義は候補として持つ。
- `frame`に同じ見た目が続いても内部状態が同一とは限らない。時間・前操作・観測進捗を保全し、No-opと遅延効果を分けて検定。見えない内部変数を「読めた」と称しない。
- SDKの`GAME_OVER`では原則RESETしか合法でない点、`ACTION6`がxy必須で有効座標域は公式に示されない点を踏まえる。`available_actions`以外の操作を勝手に発行しない。

### 4.2 操作意味と因果学習

- 各ゲームで`ACTION1..7`の意味を**操作前に既知と仮定しない**。公式は1–4の方向を典型とするがゲームごとに異なる。初回は最小限の可逆・低リスクプローブを設計し、`観測前 / 選択理由 / Action+引数 / 観測後 / 差分 / 遅延 / 因果信頼度`を保存。
- 逆操作、可逆移動、クリック、取り消し、衝突、継続押下、インタラクション、状態依存操作を、観測実験として評価。1回の時系列相関だけで因果確定せず、再実験・対照・予測当否で更新。
- ACTION6座標は候補対象の重心・端点・接合点・対称軸・ラベルから局所候補を生成し、**画面全格子の無差別クリックを標準戦略にしない**。`ACTION7`は戻す意味が保証されると仮定しない。
- 仮説に`適用条件、予測変化、必要観測、反例、成功/失敗頻度、費用、可逆性`を保持。操作結果が予測と違えば対象・原因・操作意味・計画のどこが崩れたか記録する。

### 4.3 目標推定と階層計画

- `levels_completed`の増分・`WIN`は確実な達成信号。中間進捗は公開画面変化、目標一致、障害物開放、数・色・パターン整合から**暫定的な**評価として扱い、代理報酬のハックを検知。
- 既知の地形/目標ならグラフ探索・最短経路、未知なら情報獲得行動、パズルなら物体関係/制約充足・反実仮想計画、反応型なら状態機械・時間/周期推定を、観測事実に応じて切替。単一万能ヒューリスティックを過信しない。
- 状態変化モデルを使った候補行動の短期予測、複数歩先の探索、リスク・可逆性・観測価値・行動数・時間・クリア見込をHDS判断で比較する。複合手順は**現場観測で毎手再計画**し、固定replayにしない。
- 画面が変わらない状態、往復振動、同一操作連打、無進捗が規定回数続いた場合、探索方針を切り替える。単なる停止ではなく、仮説改訂・追加プローブ・別計画・残予算配分へ結ぶ。
- レベル移行時は、同一ゲーム内の学習を保ちつつ、配置変化・初期条件差を再同定。他ゲーム間では汎用原理のみを転移し、ID対応の答え表を使わない。

### 4.4 HDSの判断Gateと実動作の分離

- HDS確定：十分な観測と認可根拠を持つ作用。既存の`HDS確定作用`契約を尊重し、実体不在なら偽造しない。
- **暫定探索Gate**：HDS未確定であっても、競技目的の下で「合法・観測可能・限定されたリスク・予算内・帰還可能性」の条件を満たす探査Actionを**暫定として**発行する。`source=exploration`, `evidence_ref`, `hypothesis`, `cost`, `rollback/replan`を記録。**探索許可をHDS確定認可へ改名しない**。
- HOLD：現在の因果主張を採択しない状態。`is_done=True`と1対1で結びつけず、情報不足なら観測・試行・計算で解消を図る。合法Actionなし、予算尽き、環境終了などの実停止条件とは別フラグ。
- 作用の合流点は単一の`ActionDispatch`：直近観測の指紋、合法Action集合、座標形式、根拠の種別（confirmed/exploratory）、現在予算を検査し、**SDKの`choose_action`でActionを返し、実際の`env.step`はRunnerだけが一回実施**することを第一案とする。既存`作用を排出する`はRunnerとの重複使用を禁止し、検証-only/変換-onlyへ責任を分ける場合は該当回帰を更新。
- 公式Starterの`main()`は初回にダミーの`FrameData`から`is_done()`を呼ぶ。`observation_space`の真のFrameとダミーを取り違えて冒頭で停止・RESET乱射しない。
- `GameAction` Enumの`set_data`が共有状態を汚し得るので、引数・reasoningの生成/消去をRun間で検査。ACTION6のx/yは0..63かつ現行盤面に意味がある候補。並列Agentでは共有Enum変異を隔離する。

### 4.5 学習記憶：事前記憶を「読むだけ」で終わらせない

- `HDS/学習系統/v0.4.2`と`記憶/事前記憶/v0.4`の**意味契約**を特定。学習された一般作用モデル・目標構造・失敗署名・仮説優先順位・探索方針のみ持ち込み、ゲームID→正解Action列を持ち込まない。
- `運転中の短期記憶（直前状態・仮説・実験履歴）`、`同一ゲームで使う抽象ルール`、`ゲーム横断の一般記憶`、`評価だけの証拠ログ`を分離。学習前後の状態hashと更新根拠を残す。
- `記憶/`が現行バンドルから除外されていることを認識し、**合法な汎用事前記憶の読み込み・ハッシュ・採用・候補順位差分**を明示的に試験。必要なモジュールが静的import検出漏れで梱包されない問題も解決。秘密Native・認証情報・評価用正解データは同梱しない。
- 失敗を記録するだけでは学習と呼ばない。反例で誤認した規則は降格・失効・保留へ更新し、翌エピソードの探索順と行動に実際に反映する。
- 比較基準：A=既存単純合法ポリシー、B=HDS判断有効/記憶固定、C=汎用事前記憶参照/更新停止、D=オンライン更新有効。**同じ公開ゲーム/seed/操作・時間枠**で完了・操作効率・転移を比較。Dの改善なしなら学習効果未実証と報告。

## 5. 検証設計と勝利への性能規律

### 5.1 一つの実験台帳に三つの数値を混ぜない

1. **公式得点**：Kaggleの数値スコア、提出ID、Notebook版、終端status。賞/順位に使える唯一の対外指標。hiddenゲームの内訳は公式が開示した範囲だけ。
2. **公開25ゲームの実測**：`games_completed / levels_completed / available_levels / actions_per_level / resets / first_action_latency / total_wall / crashes / HOLD / stagnant_actions`。可能なら公開の人間基準と同じRHAE、不可なら到達と操作数を別表示。
3. **学習効果**：A/B/C/D比較の適応前後、未見転移、原因仮説の更新/再利用、失敗による後退、状態hash。局所的に進捗したことだけでは一般学習と断定しない。

テスト群は**開発ゲームと未見転移ゲームを事前分割**し、固定seed/環境版/予算を保存。25公開ゲームを最終的に全数評価するが、同じ固定holdoutへの反復過適合を監視する。単一ゲームの手作業攻略はそのゲームに限る観測であり、他ゲームの成功根拠ではない。使用する公開環境のロジックの直接読解・hidden state抽出を評価中Agentへ通す行為は禁止。評価器はゲーム内部へアクセスして正否を測ってよいが、Agentからは公開観測だけを扱う。

### 5.2 スコア改善の優先度

優先順位の基本：

1. 全体故障を減らす：gateway初動失敗、依存不備、Action違反、`HOLD`による全棄権、ゲーム全体の中断。
2. ゲーム横断で最初のレベルを実際に突破する観測・操作・目標推定能力。
3. 複数レベルを連続突破し、後半に向けて学習を使う能力。
4. RHAEの低い**クリア済み**レベルで、無駄手の因果を特定し効率化。
5. プラットフォーム完走確率の改善、難ゲームへの処理時間配分、別手法・合法公開モデルの採否。

ただし固定順位ではなく、`期待公式RHAE増分 × 未見ゲームへの横断性 × 検証確度 ÷ 実装/実行時間`で更新。公開の汎用視覚モデル・世界モデル・プランナ・探索アルゴリズムも、公式ルール・ライセンス・9h・ネットオフライン・Native非開示を満たす範囲で比較。既存HDS資産を動かさず外部ブラックボックスに全処理を委譲した場合はHDS学習の実証と呼ばない。性能が勝る合法基線を排除しない一方、HDSの増分寄与を計る。

### 5.3 自動停止を避けるが、無限探索も避ける

- Game/Level単位に残時間・行動数・no-progress閾値を設定し、後半の加重とクリア見込みで再配分する。閾値は公開実測で校正。80Actionや1Actionの固定上限を無批判に継承しない。
- 9時間Notebook制限より十分前に処理を終えるよう安全余裕を設定（初期案：**実行制御7時間30分以内、残り90分を起動揺らぎ/片付けへ**。公開計測とKaggle運用に応じて変更）。GPU性能、gateway cold-start、各ゲーム時間枠は現場で実測。
- Gateway起動が遅い/不安定な既報がある。**起動待ち／モジュールimport／runner開始／初回Action／実ゲーム行動／自動採点**を個別計時。`curl --retry 999 --retry-max-time 600`等を固定で繰り返して無駄にした場合、ネットワーク障害なのか操作能力ゼロなのか切り分ける。
- GAME_OVERで無謀なACTIONを送る、ACTION6不正、None frame、重複step、Enumの座標残留、ログ肥大化、メモリリーク、全ゲーム停止、Notebook timeoutを回帰対象。
- Kaggle competition modeは環境ごとに`make`一度、ゲーム全体RESETを任意の再挑戦に使えない（レベルRESETへ変換）、scorecardは一枚等の制約。公開オフラインで何度も実験できることを**競技本番の再プレイ可能性**と取り違えない。

## 6. 公式提出とエラー再提出の状態機械

**厳密区別：**「Notebook Commit/Save & Run All」「Kaggle competition submission受付」「公式スコア確定」「賞の資格」は独立状態。`submission.parquet`内のdummy scoreを本採点結果に変換することはできない。

| Kaggle実状態 | 記録する状態 | Codexの行動 |
|---|---|---|
| Notebook build/Save&Run失敗、API送信自体失敗・提出履歴増加なし | `NOT_SUBMITTED` | 直接原因修正、再検査、**実際の残枠があれば当日再試行** |
| competition `PENDING`/`RUNNING`、スコア未確定 | `IN_PROGRESS` | 同IDを追跡。重複送信しない。ローカル開発は進行 |
| `ERROR`、kernel timeout、grader失敗、`COMPLETE`でも`errorDetails`があり数値scoreなし | `TERMINAL_ERROR_NOT_SCORED` | ログ・環境・gateway/依存/Action系を分類→最小是正→残枠・受付可否を照会→**許容される限り同日何度でも再提出** |
| `COMPLETE`等の終端、エラーなし、数値score確定（**0.00を含む**） | `SCORED_ACCEPTED` | 正式スコア確定。良否を分け、次の日/次枠の改善候補を準備 |
| 状態不明、`score=null`のみ、API表示不整合 | `UNVERIFIED` | 成否を決めない。公式履歴・詳細API・利用枠を再照会 |

**エラーを「当日の採点成功枠を使った」と見なして翌日待ちするな。** 公式が許容し残枠がある場合には同日何度でも修理・送信を繰り返す。一方、**エラーなら無条件に上限無制限**とも断定するな。実際の`submission-limits`とAPI結果が支配する。無変更・同原因の無限連打は禁止。合法な確定`0.00`は失敗に見せかけない。新アカウントでの上限迂回は禁止。

公式上限は原則1日1件の成立した提出、最終選択2件。採点に失敗した場合の枠の挙動はKaggleの**現在の実値**で判定する。前例としてARC3で同日複数エラー後の成功報告があるが、全エラーの枠返還が保証された公式契約ではない。**採点可能な新しいAgentがローカルで実働すると確認できた段階で公式提出へ進み、意図的な0Actionダミーで貴重な正常採点枠を消費しない。**

## 7. 競技期限と成果物

- 2026-10-28現在、締切は**2026-11-03 08:59 JST**。早い公式採点・数値改善・最終2候補選定を優先し、Notebook送信を締切直前まで延期しない。
- 提出時には「公式スコア現値 / 前回 / 増分 / ゲーム・レベル到達（公開検証） / 作用効率 / 時間 / Notebook版 / source SHA / 採点status / 残枠 / 次の改良」を必ず記録。
- 競技入賞の公開要件を満たすことがHDS中核開示を要求するなら、**秘密中核を公開せず**、公開可能なAdapter/汎用Agentだけで資格が成立するか法的・規約的に確認。適合不能なら「技術的高得点」と「賞の受給資格」を別報告し、Owner判断なしに開示しない。
- 正本化する際は新3点を`運用/ARC3-RUN-003/v3_0/`等へ保存、`運用/ARC3文書正本.md`の参照・hashを更新。v1/v2本文と運転履歴は保持。

## 8. 受入検査の必須条件

| 受入項目 | PASS条件 | 不合格時 |
|---|---|---|
| 状態確定 | `57527856`の現状を実APIで照会し、status+error+scoreを固定 | 推測で完了扱いせず再照会 |
| GameAction実行 | 少なくとも複数の有効Actionを観測に応じ選択・実行、**1Action=1step**、座標/状態合法、初回観測正しい | Agent/境界/Runnerを修正 |
| 公開25ゲーム | 全数を実際に実行し、到達・消費・停止理由の母数と結果を記録 | 原因別に再走・修理。不可なら不完走理由 |
| 競技能力 | 同条件の現行基線よりレベル到達/クリアゲーム/推定RHAEが改善。失敗も併記 | 改良を性能成果と称さず別案 |
| HDS学習 | A/B/C/Dで状態更新の実体・判断変化・未見転移・反例更新を記録 | 学習は未実証と判定し原因探索 |
| Kaggle本採点 | 少なくとも1件`SCORED_ACCEPTED`に到達し数値を保存。後続改善版の公式結果と比較 | エラーなら残枠照会→同日合法再提出 |
| 品質/履歴 | 9h制限、ネットなし、依存、秘密、権限、正本・旧履歴保持 | 具体原因修正、保護対象は停止・相談 |

**本仕様の完了は「技術上の最小条件」を満たしたことではない。ユーザーの最終目的は**首位を狙う競争力と、実働した学習機械の実証**であり、得点改善・横断学習・公式評価を期限まで反復する。**
