## 1. 最上位目的

**既存資産で一度公式提出し、その公式スコアと経路を実測したうえで、攻略能力を開発・検証し、公式再提出による更新を大会期限まで反復する。**

成功の定義は「Notebook実行成功」でも「提出受理」でも「テスト合格」でもない。

1. 公式の提出ID・Notebook版・コードSHAに結び付いた**公式スコア**を取得する（数値0も有効）。
2. 実際のゲームで観測→判断→**合法な行動**→結果→記憶・推論・適応が動くagentを成立させる。
3. 固定した公開試験と公式評価の両方で、前回版との差と失敗を追跡する。
4. 提出枠を守り、原則1日に1度の公式評価機会を継続的に活用する。提出不能日も原因と次回実行点を残す。

本版はv1.0の不当なE5事前承認・提出後停止、v2.0の**採点待ちの制御欠落**・**実行能力の未接続**・**継続運転の仕組み不備**を是正する。旧版は履歴として保持する。

## 4. 最優先の硬い受入条件：公式スコアの取得

`SCORE_READY`は以下の**全条件**が揃った場合だけ成立する。

1. Kaggleの公式提出履歴から対象提出IDを再照会した。
2. 公式処理が採点完了状態であり、**Kaggle自身が返した数値のスコア**を確認した。`0`も合格。`null`・空欄・ローカル想定点は不合格。
3. 提出ID、受付日時、Notebook slug/version、対応コードSHA、公式スコア種別と値、公式状態・取得時刻を一組として保存した。
4. 公式がエラーを返した場合は失敗と理由を保存し、成立と取り違えなかった。

`PENDING`／`RUNNING`／Notebookの`COMPLETE`／`submission.parquet`の`score=1`／提出受付のみは**SCORE_READYではない**。成績を推定値で補完してはならない。

採点待ちは無期限の無人放置にしない。既存提出IDを15分後・以後30分〜1時間を目安に再照会し、時刻・前状態・新状態・APIエラーを追記する。連続実行時間が足りなければ、次回起動で同じIDを再取得できる再開点を残す。数時間動きがなければ、キューとNotebookの実行ログ、競技側状態を診断する。重複提出で解消を試みない。

**公式スコア取得前に攻略最適化・学習成功の主張・改良版の追加公式提出へ進まない。** 実施できるのは採点状態の監視、提出経路の失敗原因調査とその最小修復。採点不能の外部阻害が実証されたら原因と再開条件をOwnerに報告する。

## 5. 公式スコアと実行能力の二重基準線

| 基準線 | 確立要件 | 何が分かるか |
| --- | --- | --- |
| B0：提出経路基準 | `57527856`など既存提出のSCORE_READY | 正規提出・公式採点経路の可否。0操作HOLDなら攻略性能は測れていない |
| B1：行動可能agent基準 | HDS／探索の出所を区別し、公式Runnerで1件以上の合法なゲーム行動・結果が観測され、公式スコア取得 | 実行するagentの現実的な初期能力 |
| B2以降：改良基準 | B1との同条件ローカル比較・公式提出版とスコア対比 | 能力改善／悪化および再利用可能な原因 |

**B0が0でも工程を止めない。** その0が無行動によるなら、B1の成立が次の課題であり、誤ったスコア最適化を始めない。

## 6. agentの必要な因果回路

必須経路：

`公式観測 → 状態・利用可能行動の取得 → 既存HDS／記憶／学習系による候補生成 → 判断・採否（根拠と権限） → 合法な行動または明示的な探索 → 環境応答 → 結果帰属・失敗署名 → 記憶→推論→適応 → 次の観測`

- 候補の自己申告`実行許可`をそのまま実行許可に昇格しない。判断のGateと実行源を保持する。
- HDSのHOLDは「この候補を確定採用できない」状態であり、**環境の観測・合法的な探索手段まで永久禁止する意味ではない**。ただし、探索する明示的根拠と実行権限を備えないまま強制作用しない。
- `NOT_FINISHED`を無条件に`is_done=True`として全ゲーム終了させる実装は、B1の受入を満たさない。検証で実際の状態遷移を要求する。
- `available_actions`、作用数上限、RESET条件、二重step防止、異常復旧を公式SDK契約に適合させる。
- 観測→行動→新観測の対応、記憶の更新前後、採否の理由を試験用に復元可能とする。private評価の秘密情報は保存しない。
- 新しい規則は仮説→局所比較→他ゲーム転移→採用の順。ログや記憶の件数増加だけで学習と呼ばない。

## 7. 公開25ゲームの評価と学習

ローカル公開資産の利用は合法な情報範囲内に限定し、公式隠し評価と混同しない。公開25ゲームを横断し、可能ならレベル単位で次を記録する。

`game_id / level / 環境版 / 観測条件 / 行動候補 / 採択理由 / 探索かHDS確定か / 実行行動 / 作用数 / 状態変化 / 到達 / HOLD / 失敗署名 / 記憶差分 / 規則候補 / 転移先 / 再現結果`

成功教師は**操作規則の因果抽出素材**とする。正解のID参照・録画再生ではない。旧進捗`14/183`、`1/25`等はその記録当時の公開条件でのみ引用し、現行再現試験と区別する。

## 8. 日次の継続評価

- `SCORE_READY`が成立した後、ローカル改良→反証・回帰→Notebook更新→Save & Run All→Competition Rerun→採点確認→採否→次課題の循環を行う。
- 原則**1日1回**、公式提出枠と期日内で検証済み最新候補を公式に評価する。枠残数は毎回APIで実測し、リセット時刻をJST深夜と決めつけない。
- 同一候補の意味のない重複送信は原則しない。提出可能な有効候補がない日は「未提出・原因・次の候補」を記録し、改善作業は続ける。無条件の0点再提出を成果と見なさない。
- 前版の公式スコア・新スコア、ゲーム到達、行動効率、HOLD・失敗署名について`previous/current/delta`を保存。公式が提供しない内訳は未観測として扱う。
- 悪化した版は原因を保存し、最後に成立した版に戻す。提出済みのNotebook・結果を後から書き換えない。

## 9. 継続運転の実体

文書に「自動継続」と書くだけで常駐運転は成立しない。Codexは既存の権限・設備で以下を実装または確認する。

1. 追記型の運転台帳（最新提出ID、採点状態、スコア、期限、次の工程、再開コマンド、監視予定時刻）。
2. セッション終了後に次回のCodex起動・既存運転機構から確実に再開する入口。既存の許可済みスケジューラがあれば利用し、無ければ未自動化を正直に記録する。新しい外部スケジュール作成・秘密情報登録は権限を確認する。
3. 同一提出IDに対する二重送信防止、日次枠の確認、公式結果の取得、途中失敗後の再試行。
4. 1タスク1指示書。単位ごとにAGENTS再読、対象・保持条件・試験・採否・次作業を固定。

`制御/現在状態.json`を無断修正せず、別の運転台帳で真の進行状態を管理できる場合はそうする。自動再開未成立なのに「無人継続PASS」と報告してはならない。

## 10. 受入試験・期限

| 試験 | PASS条件 |
| --- | --- |
| T0：公式結果 | B0スコアがKaggle一次情報と一致し、ID・SHA・版・時刻を保存 |
| T1：実行 | ローカル公式Runner上で実際の合法な行動と環境変化を確認、0操作HOLD専用試験では代替不可 |
| T2：学習 | 記憶→推論→適応の具体的差分、転移条件・反証・失敗を保存 |
| T3：公式能力 | B1以降の公式採点結果を取得し、B0との差と性質を説明 |
| T4：継続 | 次回の起動・監視・日次枠判断・再開点が再現可能 |
| T5：保持 | HDS中核・事前記憶・規範・過去ログ・秘密保護が維持された |

公式最終提出期限：2026-11-02 23:59 UTC（日本時間2026-11-03 08:59）。エントリー要件・Notebook制約・提出枠は着手時に公式一次情報を再確認する。期限前に余裕を置いて最良版を提出・状態確認する。

## 11. 最上位禁止事項

- 公式スコア未取得なのに「取得済み」「最適化成功」とすること。
- Kaggle Notebook `COMPLETE`、Parquetのplaceholder、受理`PENDING`を公式採点済みと扱うこと。
- 採点待ちで無期限停止し、その監視・再開状態を保存しないこと。
- 行動しないagentのテストPASSを攻略成功と見なすこと。
- HDS候補の無審査実行、根拠のない中核改変、固有ゲーム回答の直結。
- 工程完了や報告を理由に、Ownerの委任範囲内の次工程を人間待ちにすること。

本仕様は**公式観測→判断→実行→帰還→更新**を、スコア・行動・版管理まで切れ目なく成立させる作業契約である。
