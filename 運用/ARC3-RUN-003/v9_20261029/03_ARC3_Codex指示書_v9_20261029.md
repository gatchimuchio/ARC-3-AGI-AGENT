## 0. 最優先命令

**実行の主語はLearning Machine。学習機械が実際にAgentを制御してKaggleで入賞することが目的である。同じ系の記憶→推論→反証→適応を観測し、学習定義の実証も同時に行え。**

既存のHDS v0.4.2／事前記憶／公式Starter／実Agent／CPU探索Agent／公開モデル／リポ資産は「手段」。学習機械がそれを選び、候補を比較し、最終Actionと次の学習状態を支配する。**単独のCPU Agentが公式採点されたことやHDSを400回呼んだことを、Learning Machineの成功としてはならない。**

1. 最初に最新状態と公式IDを読み、**本当に不足している機能を特定して改造を始めよ**。監査や資料作成のみで終えるな。
2. **HDS/学習系統/v0.4.2のソフトウェア実装コアは必要なら改造・再設計してよい。** 候補生成・推論・反証・記憶・採否・行動Gate・ゲーム横断継承・予算を実働させる。関数ごとのOwner承認を待たない。修理後に旧版との差・回帰試験・学習因果比較を必ず行う。
3. **変更禁止**：リポジトリAGENTS.md、制御/現在状態.json、Ownerの目的／権限、HDS Native／神域原理／HDS理論原本、秘密ログ、認証情報。保護対象の変更・公開を自己権限化するな。
4. **ゲームID・レベルID・frame hash・seedによる解答分岐、固定Action列・replay lookup・隠し正解／evaluator内部stateの流用は禁止**。公開観測と許可された一般学習だけで攻略する。
5. 成果は同一条件の previous/current/delta と本番数値scoreで判断する。コード追加、テスト数、ログ件数、Notebook通常COMPLETE、HDS update回数は競争能力の証拠ではない。
6. 通常の技術試行・ローカル検証・許可済みKaggle提出の範囲で自律継続。実残枠が0、または提出がPENDINGの間も次の改良を続ける。追加のアクセス権・公開義務との衝突・明示的な保護境界が発生した場合だけ停止して根拠を報告する。

## 2. 最初の原因分類

次を明示的に観測し、支配要因の順を決める。

| 既知の実体 | 所在 | 実測から言えること |
|---|---|---|
| 現行HDS基底 | HDS/学習系統/v0.4.2 | 経験・推論・適応の実装原型はあるが、競技Actionの実主体化は未成立 |
| HOLD提出Agent | 接続/ARC3提出agent.py | MAX_ACTIONS=1、一般のGameActionを出さず照会後HOLDする |
| CPU探索Agent | 接続/ARC3公開探索agent.py | 公開Frameと合法Actionで探索できるが、実装コメントにもHDS非搭載と明記 |
| 公開CPU提出builder | 道具/ARC3公開CPU提出物/cpu_builder.py | 新規提出v2のNotebook source再現に有用。HDS搭載版builderではない |
| HDS候補経路 | 接続/共通観測経路.py | 実行許可Falseを伴う候補・保留。暫定探索Actionを代行する実行権限はない |
| 観測一巡・記録 | 接続/観測駆動一巡.py | 既存の記録を処理する。SDK stepや実作用の権限を発行しない |
| 旧model-guided v13 | 既存Notebookと保存公式履歴 | 公式28.07は強い競技比較基準。ただし現行LMと同一コードではない |

**第一仮説**：必要なのは「安全なHDS HOLDを強制解除すること」ではなく、**学習機械が決める暫定Action Gateと合法探索・反証更新を作ること**。知識の確定HOLDと行動実験の採否を別状態として扱う。

**第二仮説**：現行のHDS照会は、参照可能な原理が行動候補まで降りない／競合により候補が空／HDS候補が採用されないのいずれか。候補数、適用条件、未採用理由を計数し真因を特定。過去5ゲーム400照会/394更新/採用0の一点だけで「候補自体0」とは断定しない。

**第三仮説**：AgentごとにHDSインスタンスを新規生成するためゲーム間転移がない。Memoryをスコープ分離して持ち越す。ゲーム固有の手順を次ゲームの正解として再生しない。

## 3. 実装：Learning MachineがActionを支配する

**既存コードを活用し、新しい二重の権威を作らない。** 公式StarterのAgentインターフェースに、ただ1つのLMコントローラを接続する。プログラム名とファイル構成は実測に基づきCodexが選んでよい。ただし責任分離を保ち、旧提出Agent・CPU提出Agentの既存sourceを破壊せず比較できるようにする。

### 3.1 最小実働APIを先に成立

概念API。実装の型・命名は日本語基底・現行コードに合わせる。

~~~text
LM.initialize(legal_prior, public_version, budget)
LM.observe(public_frame, legal_actions, state, level)
proposals = LM.request_generators(knowledge_state, candidate_generators)
decision = LM.select_action(proposals, uncertainty, information_gain, cost, risk)
assert dispatch_authorized_by_LM(decision)
response = SDK.step(one_legal_action)
LM.update(observation_before, action, public_response, prediction_residual)
LM.transfer(generalized_memory_only)
LM.stop_or_replan(reason, remaining_budget)
~~~

必須条件：

1. 観測：初回のNOT_PLAYED／NOT_FINISHED／WIN／GAME_OVERを区別。Frame列・available_actions・full_reset・levels_completedを正しく読む。
2. 候補：HDS語彙、CPU探索、構造推論、既存model-guided、外部公開Plannerが同じインターフェースで**候補と根拠・費用・不確実性**を返す。ゲームIDで生成器を固定しない。
3. **選択主体**：Learning Machineが現在の知識・失敗・仮説・予算から候補・情報獲得プローブを採否する。外部Agentが先にActionを確定してHDSにログだけ残すのは禁止。
4. **暫定実行**：知識が未確定でも、合法性とリスクを満たす探索ActionをLMが承認できる。HDS規則の確定HOLDを変造しない。候補ゼロならfallbackの理由・試行対象・次の観測期待を明示。
5. 送信直前：現SDK状態と指紋、Actionの合法集合、ACTION6のx/yが0..63の整数で実盤面に矛盾がないこと、GAME_OVERのRESET以外禁止、残時間／残Action、重複stepを検査。
6. 応答：**1選択=1SDK step**。更新前後の可視変化、level/状態、動き・ゴール・Action意味を記録して次候補へ反映。結果が同じ見た目でも隠れ状態が不変と断定しない。
7. 共有：レベル内の物体とゲーム内の因果は局所記憶、一般化可能な探索・失敗・予算だけをゲーム横断記憶。共有状態は並列安全に設計し、スレッド間のAction Enumのmutableな引数を守る。
8. 予算：初期80手の旧上限を固有ルールとしない。実績と9時間制限からゲーム／レベルに配分。後半レベルの加重得点と進展確率を考慮し、延長が無効なら停止。

**G1最小証拠**：少なくとも複数公開ゲームで複数の合法Actionを連続実行し、HDS/LMにより下位部品のAction選択または予算が実際に変わる。Actionログの出所・採否・観測後更新を追えなければ、LM主体の成立と認定しない。

### 3.2 世界モデルと実行可能な学習へ

- 公開フレームから領域・色・物体・位置・境界・移動・クリック対象・操作差分を抽出。接続/図式観測.py、図式作用教師.py、形状配置、配色、鎖、鏡像、列図式など現行部品を有効範囲つきで再利用。
- ACTION1～4移動、ACTION5インタラクト、ACTION6座標指定、ACTION7取り消しの意味は**ゲームごとにその場で実験同定**。説明文にない規則をgame_idで埋め込まない。
- 予測される差分と実際の差分から操作効果仮説を昇格/降格。WIN、level増分、game_over等の公的フィードバックと可視差を別記録。正解を見られない場合も不確実性つきで再計画。
- 「同じ試行を繰り返す」「全80手で1レベルも進まない」「有効座標が一切選べない」を単なるロギングで終わらせず、原因を特定して次Action政策へ反映。
- 既存の外部model-guided v13のソース／モデル／許諾を調査し、得点再現・オフライン運用が可能なら候補器の一つにする。単体v13とLM搭載版を別計測。外部の公式28.07をLM版のスコアとしては記録しない。

### 3.3 v0.4.2コア修理の判断ルール

改修が必要になる症状：

- そもそも有用な次作用候補が作れない、証拠を含む仮説の形式が不足。
- 認識のHOLDが合法探索を全停止にしている。
- 照会・更新はあるのに将来の候補順位／行動が変わらない。
- ケース固有記憶と一般知識が混ざる／次ゲームへ届かない。
- 反証から適用条件の縮小・規則失効・rollbackができない。
- HDS採否が外部モデルの提案に上書きされ、監査不能。

その際の改造手順は、**失敗signature→再現用fixture→ソフトウェア実装コア最小改造→単体＋統合→以前と同条件のA/B→回帰→採否**。v0.4.2と変更後の版は両方起動できる状態を優先。既存公開packageのシリアライズ互換と履歴は保つ。HDS Framework／秘密Nativeの原文を書換えない。

## 4. 学習の定義を反証するA/B/C/D/E

一切の単独成功を学習証明へ一般化しない。

| 腕 | 部品と設定 | 学習機械の役割 |
|---|---|---|
 A: 下位のみ | 同一のCPU／外部候補器、HDSなし | 外部の単独能力 |
 B: 照会のみ | Aと同じAction、HDS照会・記録ON | 非因果的な同居効果 |
 C: 判断のみ | LMが候補採否、経験による意味状態の更新は完全固定 | 判断制御の増分 |
 D: 完全LM | C＋記憶・規則更新・反証・後続Action反映 | 実際の学習による増分 |
 E: 横断遮断 | Dからゲーム間一般記憶だけを遮断 | 横断転移の寄与 |

- **同一条件の固定**：対象ゲーム・版・seed・初期frame・候補器・合法Action集合・Action budget・壁時計・SDK score手続き。因子を一つずつ変える。AとDで方策や依存を同時に変えた場合は解釈しない。
- **Cはreadonly**：既知の「照会だけでpickle表現が変わる」問題を無視しない。深いsnapshotと意味状態diffを採る。必要なら照会側をコピーに分離。単にupdateメソッドを呼ばないだけでは固定対照と称さない。
- **Dの因果証拠**：異なる観測→経験の抽出→記憶（規則、信頼、適用域、失効、反例）→次観測で採否/方針変更→実Action変更→level/RHAE参照指標の差。変わらなければ「学習未成立」と明記し原因修理。
- **ゲーム横断**：Agentごとに新しいHDSを作る現行分離を改造し、共有可能な抽象だけを持ち越す。単に同一IDをリプレイして勝つのはEの成功ではない。公開25ゲームは以前から使用済みであり真の未見転移の証明にはならない。後出しでholdoutを選ばない。
- **評価形式**：games/levels/勝利数、操作数、無進捗、invalid、SDK参照score、公式score、LM Action採用数、記憶変化を分母・previous/current/deltaつきで別掲。小標本は限定結果と書く。採用しなかった候補や失敗例も残す。

4. PENDING/RUNNINGは追跡、ERROR/timeout/採点なしは原因・本当の残枠に従って修復・許可された再送、COMPLETE＋数値score（0.00含む）は正式受理。勝手な日次上限回避や別アカウント提出は禁止。
5. 公式28.07と新しいLM版の**公式数値同士**を比較し、どの部品が採否と実Actionを支配していたかも別記。公式高得点＝HDS学習因果の自動証明ではない。
6. 完全な公開義務・賞資格を満たすか独立確認。公開できる部分だけで成立しないと判明した場合、秘密Nativeを開示せずOwnerへ判断点を提示。

## 7. 実験一周ごとの判定方式

改善作業は**一つの原因仮説ずつ**。以下を統一形式で残す：

~~~text
[RUN] 日時、目的、責任Agent、Git HEAD、dirty tree、SDK version、Notebook version
[BASE] previousのsource SHA、公開ゲーム集合・seed・壁時計・Action予算・scorecard
[CHANGE] 支配失敗signature、実装差分、改変したLM core／候補器／Adapter
[LM] 候補生成/選択/HDS採用/暫定探索/実Action/記憶更新/転移/反証
[TEST] targeted、全回帰、合法Action/1step、ゲーム内/横断AB、ゲーム完走
[MEASURE] previous/current/delta、分母、25ゲーム、level、勝利、Action、RHAE参考値、時間、error
[OFFICIAL] submission ID、status、score、Notebookとsource hash、残枠、旧28.07との差
[DECISION] ADMIT/HOLD/REJECT、次仮説、rollback、既知限界、再識別・公開・秘密検査
~~~

- ADMIT：能力と安全性が同一条件で改善し、LM因果の限定が明確。mainに採用。
- HOLD：故障は修ったがscore差未確認、または一部ゲームでだけ効果、統計・出所が不十分。主経路へ性能成果として昇格しない。次の測定・別仮説へ。
- REJECT：違法、データ汚染、得点悪化、学習帰属不能、著しい時間超過、回帰失敗。隔離・元版へ復帰、原因と再発防止を記録。

## 8. 非停止条件・停止条件

**止まってはいけない**：資料が完成した、既存テストが通った、HDSを呼んだ、Notebookを保存した、公開ゲームを試した、合法なActionを1回出した、daily枠0、PENDING、スコア改善0で原因未追究、など。いずれも次の因果検証・改良を開始する。

**止まるべき**：AGENTS.md／制御状態・秘密Native・HDS理論正本の改変や公開が不可避、Kaggle規約・権限上の拒否、資格情報が未設定で許可された方法で復旧不能、明確な追加外部権限・賞公開対象の選択が必要、不可逆で危険な操作の範囲が不確定、など。何が必要かを一問で示す。

## 9. 最終報告の必須項目

1. **実行した内容**：触れたコード、修正したHDS v0.4.2実装、保護した正本、通した回帰、Git採否。
2. **実際の競技結果**：最新公式 ID/score/status と既存28.07の差、期限・残枠。未確定は未確定と書く。
3. **Learning Machineの実証結果**：どの経験が何の規則を変え、未来のAction・レベル・RHAEがどう変わったか。A/B/C/D/Eの対照・限界。
4. **失敗と次の仮説**：最も大きな未解決原因、修理案、同条件追試、次回公式採点。
5. **入賞状況**：実際の順位・資格・入賞の確定事実。提出完了や競技点改善だけで「入賞」とは書かない。

**目的はCodexを動かすこと自体でも、HDSの形式的適合でもない。ラーニングマシンを主体とした本物の攻略と、その学習による能力改善でKaggleに勝つこと。**
