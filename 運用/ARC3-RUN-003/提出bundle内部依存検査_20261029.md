# 提出bundleの内部依存検査（2026-10-29）

## 問題と変更

Notebook構築器は静的importを辿って自社内ソースをbundleに含めるが、明示した内部モジュールが存在しない場合も検出を続け、bundle生成を成功させていた。提出Agentの必須依存が欠落しても、その後のimport時まで失敗が表面化しない。

`接続` と `hds学習系統` の明白な内部モジュール参照が存在しない場合、構築を `ModuleNotFoundError` で停止する。`__init__.py` を持たないnamespace packageも実在するディレクトリとして扱い、必要な空namespaceがbundle展開時に失われないよう記録する。`from package import name` は属性とサブモジュールが構文上曖昧なため、存在する子モジュールだけを追跡し、属性欠落・実行時の動的importは別の隔離import検査で判定する。

## 検証と限界

- Windows、Python 3.12.10。`検証/test_ARC3提出依存閉包.py` は20 passed、対象2ファイルのRuff PASS。
- 既存のNotebook構築回帰は4 passed、1 deselected。除外した1件はこのworktreeに公開ゲーム入力がないため、対象を明示して選外とした。実Starterを使うfresh importは新規検査で別途実施したが、除外した実ゲーム運転の代替とはしない。
- 欠落した明示内部import、namespace root・多階層・相対import・空namespace、属性と子モジュールの区別、隔離subprocessでのimport成功／失敗を検査した。動的依存はimport時に実行された範囲のみ確認。
- 現main相当の既存HOLD bundleは、修正前後とも34ソース、SHA-256 `701f7fc97707adc9c51292194d0a8660f59e9fc7ffc0aef30db452f6e8ef6c9e` で一致した。これは提出Agentの攻略性能やKaggle本番動作を示さない。
- 修正後の構築器SHA-256 `53871e377ef0f5a37e346e3b5fd7affbf34d6e6f1a5bed9cb1479efdc9474081`、検査SHA-256 `9661f1e9ed09932132c63ca313592b862654074ef7fd55825e4db7267d4f0908`。実施時の基底commitは `bef4d20a3f2d69959ecbb45fd51349120c6cda24`。

静的importの必須判定は `try/except` 内の明示importにも適用する。将来、意図的な任意依存を導入する場合には別の契約が必要。関数実行時に初めて呼ばれる動的import、Notebook実行、競技Gateway、公式スコアは未検証。
